Scoring Engine Audit

Why the report shows "Pre-Maximo" as the next step

Trace from question → Pass 1 logic → stage gating → hero selection → rendered output

Summary finding

Two "pre-Maximo credit" milestones — IC-1-PROG and SC-1-REG — were marked UNMET by the scoring engine because the user skipped their checkbox options in favour of higher-level options in the same question. Both milestones gate FSM Stage 1, so the engine treats the user as not having completed Stage 1 at all, surfaces them as the top priority actions, and the details card renders IC-1-PROG's only touchpoint — "Pre-Maximo — Paper / Spreadsheet / Standalone Inspection Tool" — as a blue product tag labelled Pre-Maximo.

The causal chain — step by step

1

Question Q-IC-MULTI — Inspections & condition capture

The user selected two options: Digital inspection records captured in Maximo (IC-2-INSB) and Meter readings logged in Maximo (IC-3-METB).

They did not select the first option: "A repeatable inspection program exists for critical assets, even if not yet in Maximo" — the option that maps to IC-1-PROG. This is a pre-Maximo credit for customers who still use paper or spreadsheets. Someone already doing digital inspections in Maximo would naturally skip it.

2

Pass 1 rule — multiselect "not selected = UNMET"

For milestone-multiselect questions, the engine applies this rule in scoring.js:

"If other options were selected but this one was not → mark it UNMET."

Result: IC-1-PROG = UNMET — even though having digital inspections in Maximo is a strict superset of having an inspection program that isn't yet in Maximo. The rule has no implied-met awareness; it treats every unchecked option as a denial.

Same pattern hits SC-1-REG. On the spare parts question (Q-SC-MULTI), the user selected SC-2-BASICS and SC-4-OPT but skipped the first option ("parts tracked somewhere, even outside Maximo") that maps to SC-1-REG. It is also marked UNMET for the same reason.
3

Pass 2 — Both milestones gate FSM Stage 1 → attainedFSMStage = 0

Both IC-1-PROG and SC-1-REG have fsmStage = 1. The attainedStage("FSM") function walks stages 1 → 5, stops the moment any assessed gating milestone is not MET. Stage 1 has two UNMET milestones, so the walk stops immediately.

attainedFSMStage = 0  →  nextFSMStage = 1

For reference, APM is unaffected — IC-1-PROG has apmStage = null — but CM-2-TRIG is UNMET and gates APM Stage 2, so attainedAPMStage = 1, nextAPMStage = 2.

4

Pass 3 — Target stages from objectives

Objectives selected: Reduce maintenance costs (APM 2/3, FSM 2/3) and Improve MRO inventory efficiency (APM 3/4, FSM 3/4). Combined target: targetAPMStage = 4, targetFSMStage = 4.

Both IC-1-PROG (fsmStage 1 ≤ 4) and SC-1-REG (fsmStage 1 ≤ 4) fall within the target range and are valid action candidates.

5

Pass 4 — Hero selection sort

Three milestones tie on the top two sort keys — isGatingNext = 1 (they gate the very next unattained stage) and isUnlocked = 1 (all prerequisites already met):

Milestone isGatingNext isUnlocked Level Obstacle ID sort
IC-1-PROG 1110"IC…" wins
SC-1-REG 1110loses to IC
CM-2-TRIG 1120loses on level

Level 1 beats Level 2, then ID alphabetical order breaks the tie: "IC-1-PROG" < "SC-1-REG". IC-1-PROG is Step 01.

6

Render — "Pre-Maximo" appears as a product tag

renderDetailsCard() in report.js extracts product names from each touchpoint string by splitting on " — ". IC-1-PROG has exactly one touchpoint:

"Pre-Maximo — Paper / Spreadsheet / Standalone Inspection Tool"

The left-hand side of the split — "Pre-Maximo" — becomes the product tag label, rendered as a blue cds-tag under "Required Maximo modules". That is the text the user sees as their next step.

The label "Required Maximo modules" is also misleading here — IC-1-PROG explicitly requires no Maximo modules. The touchpoint was written as a data convention to credit pre-Maximo practice, not to describe a product requirement.

Three ways to fix it

Option A — Implied-met logic in Pass 1 Code change

After resolving multiselect questions, walk the prerequisite graph and promote any UNMET milestone to MET if a milestone that already resolved to MET lists it as a prerequisite. This mirrors the implied-met logic the ladder questions already use, and fixes the pattern for any future milestones that have the same relationship. Change is isolated to scoring.js resolvePass1().

Option B — Mark pre-Maximo milestones as implied in the binder Data change

Add an implied flag to the IC-1-PROG and SC-1-REG question options so Pass 1 knows selecting IC-2-INSB automatically implies IC-1-PROG is met. Change lives in Logic/Question_Binder.xlsx and flows through to data/assessment.js on rebuild. Requires a small code hook in Pass 1 to read the flag.

Option C — Remove IC-1-PROG and SC-1-REG from FSM Stage 1 gating Register change — no code

Set fsmStage = null for both milestones in the Milestone Register. They are "pre-Maximo credit" milestones that were never meant to block a customer already operating in Maximo. Removing them from the stage walk means they cannot gate attainedFSMStage and will not surface as hero actions for mature users. Rebuild with build_report_data.py. No scoring code changes required — this is the lowest-risk, fastest fix.
