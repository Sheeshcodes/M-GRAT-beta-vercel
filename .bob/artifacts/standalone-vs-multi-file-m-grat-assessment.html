Standalone vs Multi-file — MAS Growth Readiness Assessment

M-GRAT · assessment-standalone.html vs the served multi-file app

General audience

What are the two versions?

The assessment exists in two forms that behave identically for anyone filling it in:

AspectStandalone HTML fileMulti-file web app
What it is A single .html file you can save to your desktop or share via email A folder of separate files hosted on a web server
How to open it Double-click the file — it opens in any browser, no internet required for the assessment itself Visit a URL (e.g. assessment.example.com) — requires a live server
What the user experiences Identical — same splash screen, same questions, same report Identical — same splash screen, same questions, same report
Who it's for Field teams, demos, email distribution, situations without reliable internet access Published product, analytics tracking, regular content updates
Keeping it up to date A developer runs one command to regenerate the file whenever the app changes Changes are deployed to the server in the normal way
Key point The standalone file is not a simplified version — it contains everything: all questions, all scoring logic, all report content. It is a complete, self-contained snapshot of the app at the moment it was last generated.

Why have both?

  • Standalone — ideal when you need to share the assessment in a one-to-one or field context: attach it to an email, open it on a laptop without Wi-Fi, include it in a sales kit. No login, no URL, no dependency on anyone's server being up.
  • Multi-file app — ideal as the live, maintained version of record. Supports server-side analytics, easy incremental updates, and proper hosting infrastructure.
One source of truth The standalone is always generated from the same source files as the live app. Running python3 scripts/bundle.py produces a new standalone that reflects whatever changes have been made to the app.

Standalone — how it's built

scripts/bundle.py assembles assessment-standalone.html from the live source files. It performs these transformations in order:

  1. Start from index.html — the full splash + assessment shell HTML is the base document.
  2. Inline all CSS — css/styles.css, css/splash.css, and css/report.css each replace their <link> tags with a <style> block in-place.
  3. Inject the report DOM — the <body> content from report.html (the full report HTML, including all injection-target ids) is inserted into the existing empty #report-view div. The <script> tags from report.html are stripped; the JS is included via the bundle instead.
  4. Add report Carbon components — report.html loads additional Carbon Web Component CDN scripts (cds-tooltip, cds-menu-button, etc.) that index.html does not. These are appended to the <head>.
  5. Build the flat JS bundle — all ES modules are concatenated in dependency order into a single non-module script, wrapped in an async IIFE ((async () => { … })()). Module syntax is stripped as follows:
    • import … from … statements are deleted
    • export default is converted to const <alias> =
    • export async function / export const — export keyword is dropped
    • export { … } re-export lists are deleted
  6. Resolve naming collisions — both report.js and app.js declare const $ and const $$ at module scope (legal in modules, fatal in a flat script). The bundler renames report.js's copies to $r and $$r at both declaration and all call sites.
  7. Apply standalone-specific JS patches — four targeted substitutions are applied to the bundled source (see table below).
  8. Strip Vercel analytics — the cdn.vercel-insights.com script tag is removed (server-side telemetry, irrelevant in a local file).

report.js — backward-compatible init() signature

init() in js/report.js was updated to accept an optional injectedResult parameter:

  • Multi-file app — called with no argument; reads result from sessionStorage as before.
  • Standalone — called by window.__reportInit(result) with the live scoring result; sessionStorage is bypassed entirely.

UI / logic change in any js/ or css/ fileRun python3 scripts/bundle.py
report.html structure changedRun python3 scripts/bundle.py
New Carbon CDN component added to report.htmlAdd the script tag to REPORT_CDN_SCRIPTS in scripts/bundle.py, then re-bundle
New naming collision introduced (new shared helper in a module)Add a rename pass to the relevant build_*_module() function in scripts/bundle.py
Known constraint The standalone relies on CDN-hosted Carbon Web Components for interactive controls (cds-button, cds-checkbox, etc.). An internet connection is required for those elements. The assessment content, scoring logic, and all data are fully self-contained and work offline; only the UI component styling and behaviour depend on the CDN.
