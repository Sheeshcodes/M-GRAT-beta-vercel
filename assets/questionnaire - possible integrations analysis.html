Questionnaire Tool
Integration Analysis

Assessment of six candidate tools for hosting the M-GRAT questionnaire externally, connecting responses to the scoring engine (scoring.js), and generating the M-GRAT report — with zero changes to the scoring engine or report renderer.

Three tools were ruled out before deep evaluation Monday.com WorkForms has no matrix question type, no multi-page support, and cannot pass a response ID in the post-submit redirect URL — three hard structural blockers. WalkMe Surveys is a Digital Adoption Platform overlay, not a standalone questionnaire tool: it requires WalkMe deployed on the host app, has no matrix type, no post-submit redirect, and no programmatic API for individual response retrieval. Marketo Forms is a marketing-automation lead-capture tool: it has no matrix question type, no conditional branching, no anonymous survey option, and stores responses as lead attributes (not discrete response objects). All three are documented below for completeness but are not viable candidates.

M-GRAT Integration Requirements

For a tool to be viable, it must satisfy all five core requirements below. Any hard blocker against a requirement disqualifies the tool.

#RequirementWhy it matters
R1Matrix question type (rows × 3 columns: Met / Unmet / Unknown)M-GRAT uses 3 matrix groups covering 11 milestone rows. No workaround preserves the UX at comparable effort.
R2Multi-page / paginated surveyAssessment spans 4 pages (Goals, Maintenance Ops, Field Service, Asset Performance). Single-page scroll is not acceptable.
R3Unique response ID passed to redirect URL after submissionThe landing page must know which response to retrieve. Without this, matching the response requires brittle workarounds (timestamp, email, browser fingerprint).
R4Programmatic API to retrieve individual responsesThe backend must fetch a specific response and map it to state.answers. Bulk CSV export or dashboard-only data is insufficient.
R5Standalone shareable link for external respondents (no account required)M-GRAT is distributed to customers and prospects who have no account on the survey platform.

Qualtrics ✓ Recommended

✅
Fully viable — purpose-built for this use case All five M-GRAT requirements are met natively. The v3 REST API supports the complete retrieve-map-score pipeline. The scoring engine and report renderer require zero changes.
  • Native Matrix Table question type — maps directly to M-GRAT's Met/Unmet/Unknown rows
  • Multi-page surveys with page breaks and block-level display logic (all plans)
  • Post-submit redirect URL with piped text {e://Field/ResponseID} — response ID arrives in the URL automatically
  • v3 REST API: 3-step async export/poll/download retrieves a single response by ID
  • Anonymous shareable links — no respondent account required
  • Conditional display logic (branch on any prior answer) on all plan tiers
  • Async export adds ~2–5 s latency — show a loading state on the landing page
  • Datacenter ID mandatory in API base URL — wrong ID returns a silent 404
  • Options flagged "Exclude from analysis" are silently dropped from exports — never use that flag

Microsoft Forms ⚠ Viable with workaround

⚠️
Viable — but with one significant workaround required Microsoft Forms meets 4 of 5 requirements natively. The critical gap is R3: there is no native mechanism to append a unique response ID to the post-submit redirect URL. A workaround exists (correlation token via hidden field), but adds implementation complexity and a small residual reliability risk. If your team already uses Microsoft 365 and does not want to procure Qualtrics, this is the next-best option.
  • Native Matrix / Rating Grid question type — rows × columns, maps to Met/Unmet/Unknown
  • Multi-section forms with branching (page-break equivalent via sections)
  • Public anonymous shareable links — no Microsoft account required for respondents
  • Microsoft Graph API allows reading form responses programmatically
  • Already included in Microsoft 365 licences — no extra procurement
  • Conditional branching (show/hide sections based on prior answers)
  • No native response ID passthrough — redirect URL is static; Forms does not append the submission ID
  • Graph API for Forms responses is partially undocumented / uses internal endpoints — not officially stable for production use
  • Correlation workaround required: embed a hidden GUID field in the form, pass it via redirect, then query Graph API filtering by that GUID
  • Graph API requires delegated or app-level M365 permission (not a simple API token) — OAuth 2.0 app registration in Azure AD is mandatory
  • Response retrieval is not real-time: Graph API does not have a filter-by-ID endpoint for anonymous Forms — you must poll the full response list and find the matching GUID

Workaround for R3 — response ID passthrough

How it works: 1. Generate a UUID correlation token and pass it to the Forms URL as a query parameter (e.g. ?token=abc123). 2. In the form, use a hidden pre-populated field that reads the token from the URL via a Power Automate flow or a thin redirect wrapper page. 3. On submit, Forms redirects to a static URL. Your landing page has already stored the token in sessionStorage before launching the form window. 4. On return, the landing page reads the stored token, queries Graph API for responses, finds the entry where the hidden field equals the token, and proceeds with scoring.

Monday.com WorkForms ✗ Not recommended

🚫
Three hard structural blockers — not viable No matrix question type, single-page scroll only (no multi-page), and no response ID in post-submit redirect URL. These are platform-level constraints that cannot be worked around without replacing the WorkForms module entirely.
🚫 No matrix question type
M-GRAT requires a rows × 3-columns matrix for Met/Unmet/Unknown capture. WorkForms has no equivalent. Splitting into 11 individual radio questions destroys the UX and creates a fragile mapping layer.
🚫 No multi-page / pagination
WorkForms is single-page scroll only. M-GRAT spans 4 thematic pages. No page-break or wizard capability in Standard or Pro plans.
🚫 No response ID in redirect URL
Post-submit redirect is a static URL. There is no equivalent of Qualtrics' piped text. The landing page has no reliable way to identify which submission to retrieve.
⚠ Conditional logic — Enterprise only
Show/hide logic on Standard and Pro plans is not available. M-GRAT's skipCondition fields would require Enterprise licensing.

WalkMe Surveys ✗ Wrong tool category

🚫
Designed for in-app Digital Adoption overlays — not standalone assessments WalkMe Surveys are triggered inside a WalkMe-enabled web application and close on completion. They cannot be distributed as a standalone link, have no matrix question type, produce no post-submit page navigation, and expose no API endpoint for retrieving individual responses.
🚫 Not a standalone survey tool
WalkMe must be deployed on the host web application. External respondents with no access to the WalkMe-enabled app cannot take the survey.
🚫 No post-submit redirect
Surveys are overlays — they close on completion. No page navigation occurs, so there is no mechanism to pass a response ID to a landing page.
🚫 No programmatic response API
The WalkMe REST API (api.walkme.com) has no survey-response endpoint. Response data is accessible only inside the WalkMe Insights dashboard.
🚫 No matrix question type
Supports single-choice, multi-choice, rating, NPS, and open text. No matrix / Likert-table type for the Met/Unmet/Unknown milestone rows.

Adobe Experience Manager (AEM) Forms ✗ Not practical

🚫
Technically capable but requires a full enterprise CMS deployment AEM Forms can build complex adaptive forms with multi-page layouts, rule-based conditional logic, and REST-based submission handling. However, it is a component of the Adobe Experience Manager CMS platform — not a hosted survey service. Deploying AEM Forms for this use case requires provisioning and maintaining an AEM instance (cloud or on-premise), significant upfront configuration, and Adobe licensing. The engineering overhead dwarfs the value for a questionnaire of this scope.
  • Adaptive Forms support complex field types including repeatable panels (closest to matrix)
  • Multi-page wizard layouts with panel-based navigation
  • Rule-based conditional logic (show/hide, calculate, validate)
  • REST endpoint for form submission retrieval — POST /submit can forward data to external REST endpoints
  • Public form URLs possible — anonymous external access supported via AEM publish tier
  • Requires a full AEM instance — AEM Cloud Service or on-premise AEM 6.5+. This is a multi-week infrastructure project, not a survey tool sign-up.
  • AEM Forms does not have a native matrix question type — a repeatable panel approximation requires custom component development
  • No hosted "survey service" — you own and maintain the infrastructure
  • Adobe Experience Manager licensing is significantly more expensive than dedicated survey tools
  • API authentication for response retrieval requires AEM service credentials — cannot use a simple API token like Qualtrics
  • If your organisation already runs AEM for its web platform, this becomes more viable — but still requires custom form component development for the matrix type

When AEM Forms could be reconsidered

AEM Forms becomes practical only if: (a) your organisation already operates an AEM instance for its web presence, (b) an AEM-certified developer is available, and (c) the assessment must live within the same CMS for brand or governance reasons. Even then, the matrix question type requires custom component development.

Marketo Forms (Adobe Marketo Engage) ✗ Wrong tool category

🚫
Marketo is a marketing automation platform, not a survey tool Marketo Forms are designed for lead capture — collecting contact data to feed CRM workflows and email nurture programmes. They have no matrix question type, no conditional branching, no anonymous response option, and store form submissions as lead record attributes (not discrete response objects). It is the wrong tool category for this use case and should not be evaluated further.
  • Standalone public landing pages — no respondent account required
  • REST API can retrieve lead records (form submission data is stored as lead attributes)
  • Post-submit redirect URL with some URL token injection
  • No matrix question type — only text, email, phone, dropdown, checkbox, radio
  • No conditional branching — show/hide logic is not available
  • No anonymous responses — all submissions are tied to a lead record (requires an email address or cookie identification)
  • Responses stored as lead field values, not as discrete response objects — there is no unique "response ID"
  • API returns lead records, not form submissions — retrieving the correct entry requires filtering by email or custom field, not by a submission ID
  • Designed for CRM lead pipeline; using it for assessment data collection is a significant misuse of the platform
  • Marketo licensing is scoped to marketing automation use cases — using it as a survey tool may violate licence terms

Bottom line

Do not use Marketo for this use case. Even setting aside the missing features, the fundamental data model mismatch — lead records vs response objects — makes it technically impossible to build a reliable per-submission retrieval and scoring pipeline without a completely custom data layer that would cost more to build than procuring a proper survey tool.

Summary Recommendation

💡
Use Qualtrics. It is the only tool that meets all five M-GRAT requirements natively, with a documented and stable API for individual response retrieval. Microsoft Forms is a credible second option if your organisation is already on Microsoft 365 and wants to avoid a new procurement — but it requires an additional correlation-token workaround and Azure AD app registration. All other tools evaluated (Monday.com WorkForms, WalkMe Surveys, AEM Forms, Marketo Forms) have structural blockers that make them unsuitable for this use case.
